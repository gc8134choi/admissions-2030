# 데이터 저장 방식 대안 (temp, 2026-10-25)

결론: **A안(정규화 JSON + 생성기)으로 진행.** 최종 의견은 사용자에게 받는다.

## 현재 규모 (portal/data 실측)
| 파일 | 크기 | 행 |
|---|---|---|
| offerings.json | 221KB | 388 (4개교) |
| policy.json | 96KB | 128 |
| subject-info.json | 134KB | 231 |
| 전체 | 약 0.6MB | |

db-schema.md 추정: 학교 30곳이면 offerings 약 1.3MB. 대학 요강(admission_rules)은 대학×모집단위×학년도×전형이라 가장 빨리 커질 수 있으나, 관심 대학만 넣으면 수천 행(수 MB) 수준으로 본다(추정).

## 대안
| | A. 정규화 JSON + 생성기 | B. SQLite(sql.js) | C. 현행 유지 |
|---|---|---|---|
| 구조 | 엔티티별 JSON, 정본(전사본·초안)에서 `tools/*.mjs`가 생성, JSON Schema + CI 검증 | `.sqlite` 파일을 브라우저가 sql.js(WASM 약 1MB)로 열어 SQL 질의 | 지금의 평탄 JSON + 화면 코드 안 조인 |
| 서버·빌드 | 불필요(생성기는 Node, 화면은 fetch) | 불필요하나 WASM 로드, 바이너리 파일이라 PR diff 불가 | 불필요 |
| 대학 요강 매칭 | 생성기가 `matches.json`(학교×모집단위 충족표)을 미리 계산. 화면은 읽기만 | 화면에서 JOIN으로 즉석 계산 가능 | 화면 JS에 매칭 로직이 흩어짐 |
| 리뷰·감사 | JSON diff가 PR에서 읽힘(감시 봇 PR 흐름과 맞음) | 바이너리라 리뷰 불가. SQL 덤프를 따로 관리해야 함 | 읽힘 |
| 무결성 | Schema + 참조 검사를 CI에서 | 외래키 제약은 좋으나 CI가 별도 도구 필요 | 검사 약함 |
| 모바일 부담 | 화면별 lazy 로드, core 27KB부터 | 첫 로드 WASM + DB | 지금과 같음 |
| 위험 | 파일 수 증가, 조인을 생성기에 미리 해 둬야 함 | 의존성(WASM) 유지, 개인 학습자 확장은 쉬움 | 대학 요강이 들어오면 한계 |

## A로 가는 근거
1. 기존 파이프라인(전사본 → build-db → portal/data, build-policy)과 CI(`--check`)가 이미 JSON 기반이라 연속선이다.
2. 감시 봇 -> 초안 -> PR 흐름은 텍스트 diff가 전제다(B는 깨짐).
3. 규모가 작다(0.6MB). SQL이 필요한 조인은 생성기가 미리 계산하면 된다.
4. "정본은 전사본, DB는 생성물" 원칙을 그대로 유지한다.

## B를 다시 볼 조건 (재검토 트리거)
- admission_rules + offerings 합계가 5MB를 넘고 모바일에서 첫 화면이 느려질 때
- 사용자가 자유 질의(학과 X의 권장과목을 가장 많이 충족하는 학교 순위 등)를 화면에서 임의 조합으로 하고 싶어할 때
- 이때도 정본은 JSON을 두고 SQLite를 **추가 생성물**로 내보내는 방식(A + B 혼합)으로 간다.

## C를 택하지 않는 이유
events가 policy.json 안에 섞여 있고(build-policy.mjs의 EVENTS 하드코딩), 과목 id가 이름에서 파생(`subjectKey`)되어 이름이 바뀌면 깨진다. 대학 요강을 붙이려면 안정 과목 코드와 별도 엔티티가 필요하다.
